Writing Specifications

Typing Output to the Target Schema

Given a target schema (--target-schema, or target_schemaview from Python), each value is converted to the target slot's range before it is written. This applies whether the value comes from populated_from, expr: or value:.

With this target schema:

classes:
  Person:
    attributes:
      id:
        identifier: true
      sex:
        range: SexEnum
      weight_kg:
        range: decimal
      smoker:
        range: boolean
enums:
  SexEnum:
    permissible_values:
      FEMALE:
        meaning: OMOP:8532
        aliases: [female, F]
      MALE:
        meaning: OMOP:8507
        aliases: [male, M]

a spec that only renames columns:

class_derivations:
  Person:
    populated_from: Row
    slot_derivations:
      id:
      sex:
      weight_kg:
        populated_from: weight
      smoker:

turns this TSV, where every value is a string:

id  sex        weight  smoker
P1  female     70.50   false
P2  OMOP:8507  81      true
P3  unknown    65.2    false

into:

{"id": "P1", "sex": "FEMALE", "weight_kg": 70.50, "smoker": false}
{"id": "P2", "sex": "MALE", "weight_kg": 81, "smoker": true}
{"id": "P3", "sex": "unknown", "weight_kg": 65.2, "smoker": false}

with the warning 'unknown' is not a permissible value of enum SexEnum.

Datatypes. Values are converted when the target range is integer, float, decimal, boolean or string, or a type derived from one of them. Other types, such as dates and URIs, pass through as they are. A value that can't be parsed, such as no for a boolean, fails the row at mapping time rather than producing output that fails validation later. decimal values are kept exact, trailing zeros included, in every output format.

Enums. A value is matched against the enum's permissible values by key, then meaning (CURIEs are expanded, so OMOP:8507 matches its full URI), then title, then aliases, and written as the permissible value's key. The first of those that matches decides; a value matching two permissible values the same way is an error, as is a value matching none. Without --strict both are warnings and the value passes through unchanged; with it, the row fails. Enums defined by a query (reachable_from, matches, concepts, include, minus, inherits) or with no permissible values aren't resolved.

Overriding the target. A range: on a slot derivation takes precedence over the target schema. validate-spec warns when that override means values won't be coerced or resolved to the target slot's range, such as range: string on an enum slot.

Joining Tables

When the source is a directory of tables, a class derivation can read slots from a second table. Name the table and the columns that link it:

class_derivations:
  Observation:
    populated_from: Visit
    joins:
      Participant:
        source_key: participant      # column in Visit
        lookup_key: participant_id   # column in Participant
    slot_derivations:
      id:
        populated_from: visit_id
      weight:
        populated_from: weight_kg
      sex:
        populated_from: Participant.sex
      born:
        expr: "{Participant.birth_year}"

Use join_on: <column> instead when both tables name the key column the same. If they do, the joins: block can be left out entirely: a reference like {Participant.sex} is joined on the column the two tables share.

linkml-map map-data -T spec.yaml -s source.yaml --source-type Visit -f jsonl data/

with data/Visit.tsv and data/Participant.tsv gives:

{"id": "V1", "weight": 70.5, "sex": "F", "born": 1980}
{"id": "V2", "weight": 81, "sex": "M", "born": 1975}
{"id": "V3", "weight": 65}

A row with no match in the joined table, like V3, gets no values from it.

Working with Auto-Generated Schemas

When working with schemas auto-generated from tabular data (e.g., via schema-automator), foreign key relationships may not be defined. The source_schema_patches feature allows you to augment the source schema with additional type information needed for cross-table lookups.

Cross-Class Slot Lookups

Use dot notation in populated_from to traverse foreign key relationships:

class_derivations:
  FlatPerson:
    populated_from: Person
    slot_derivations:
      id:
      name:
      org_name:
        populated_from: org_id.name  # Get 'name' from the Organization referenced by org_id

This requires: 1. The source schema defines org_id with range: Organization 2. The referenced objects are indexed. map-data indexes its YAML or JSON input for you; from Python, call transformer.index(container_data, "Container") before mapping. For tables, use joins instead.

Inlined Nested Data

The same dot notation also traverses inlined nested objects (tree-shaped sources such as XML, JSON Schema, OWL, or EML), walking directly into the nested structure:

class_derivations:
  SchemaDefinition:
    populated_from: EMLDocument
    slot_derivations:
      title:
        populated_from: dataset.title  # 'title' inside the inlined 'dataset' object

A segment is treated as inline traversal when the source slot is declared inlined / inlined_as_list, or when the value is a nested object at runtime. No ObjectIndex is needed — the nested data is already present. Mapping each item of a multivalued inline list through a sibling class derivation is not yet supported (#265); such a path raises an error naming the multivalued segment.

Schema Patches for Auto-Generated Schemas

If your source schema doesn't define FK relationships (common with auto-generated schemas), use source_schema_patches to add them:

source_schema_patches:
  classes:
    Person:
      attributes:
        org_id:
          range: Organization  # Add FK relationship

class_derivations:
  FlatPerson:
    populated_from: Person
    slot_derivations:
      org_name:
        populated_from: org_id.name  # Now works with the patched schema

The patches use standard LinkML schema YAML structure and are applied before transformation runs. This keeps your auto-generated schemas reproducible while adding semantic information discovered during transform design.

Identifiers

When the target schema gives a class an identifier slot (identifier: true), every record of that class needs a value for it. A class derivation provides one in one of two ways:

  • Derive it like any other slot. Use this when other records refer to the id — a natural key that a referring spec can recompute, e.g. uuid5("https://example.org/Visit", str({participant}) + ":" + str({visit})).
  • Mint it with mint_ids: true. The id becomes a UUID5 hash of the record's own content. Use this for records nothing refers to.

If a derivation does neither, linkml-map refuses to produce output and names the class derivation. With --continue-on-error, it reports the problem once, writes the records without ids, and exits non-zero. Without a target schema there is no identifier to check.

Turning minting on

Minting is off unless asked for. It can be turned on, or off again, at three levels; the most specific setting wins:

mint_ids: false              # 1. the whole specification (also the default)

class_defaults:              # 2. every derivation of a target class
  MeasurementObservation: {mint_ids: true}
  Quantity: {mint_ids: true}

class_derivations:
  MeasurementObservation:
    populated_from: lab_results
    mint_ids: false          # 3. this derivation only
    slot_derivations:
      ...

Abstract and mixin target classes are skipped, since they have no records of their own. An id derived by an ancestor derivation (is_a) counts as derived.

When specifications are merged from several files, mint_ids and class_defaults must agree across them: conflicting values are an error rather than being decided by file order. A single file per directory holding these settings applies to everything merged with it.

What a minted id is

id = uuid5(uuid5(NAMESPACE_URL, "<target schema id>/<TargetClass>"), canonical(record))

The record is hashed as emitted — after derivation, without hidden slots or the id itself. Its canonical form sorts keys; drops nulls, empty lists, and empty objects; sorts list items unless the target slot is list_elements_ordered; writes every number in one fixed-point form (so 5, 5.0, and 5.00 agree, and floats are rounded to 15 significant digits first); and includes nested objects with their own minted ids.

The same record always gets the same id, whatever the row order, chunking, or parallelism, and identical records get identical ids, so duplicates are easy to find. But these are content hashes, not stable identifiers: changing any emitted value — or adding a slot that has a value — changes the id. Don't mint ids for classes other records refer to; give those mint_ids: false so a forgotten derivation is caught. The background is in #342.
